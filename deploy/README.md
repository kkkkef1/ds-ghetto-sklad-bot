# Деплой и конвенция для будущей инфраструктуры

## Один бот = один каталог, один systemd-юнит

- Код: `/opt/bots/<name>-bot/` (например `/opt/bots/sliv-bot/`).
- Юнит: `discord-bot-<name>.service` (например `discord-bot-sliv.service`).
- Общий системный пользователь `bots` для всех ботов (см. шаги установки в
  главном README) — исполняемые файлы не должны требовать root.

Единый префикс `discord-bot-*` в имени юнита сделан специально: когда
появится главный бот-оркестратор, он сможет находить и перезапускать любой
из остальных ботов по маске (`systemctl list-units 'discord-bot-*'`,
`systemctl restart discord-bot-<name>`), не зная заранее полный список.

## Права для будущего бота-менеджера

Бот-процесс сам по себе не имеет прав root и не может вызывать `systemctl`
напрямую. Когда будете делать главного бота (доступ только для
`437954847015436288`), самый чистый вариант — не давать боту прямой доступ к
systemd вообще, а дать ему узкий sudoers-файл, разрешающий без пароля ровно
эти команды и ничего больше:

```
# /etc/sudoers.d/bots-systemctl
bots ALL=(root) NOPASSWD: /usr/bin/systemctl start discord-bot-*, \
                           /usr/bin/systemctl stop discord-bot-*, \
                           /usr/bin/systemctl restart discord-bot-*, \
                           /usr/bin/systemctl status discord-bot-*, \
                           /usr/bin/journalctl -u discord-bot-* -n *
```

Главный бот вызывает `sudo systemctl restart discord-bot-sliv` и т.п. из
Node (`child_process.execFile`, не `exec`, чтобы избежать shell-инъекций через
имя бота). Список управляемых имён держите в самом главном боте (allowlist),
а не берите из ввода пользователя как есть — так даже при опечатке в имени
никакая посторонняя команда выполнена не будет.

Проверку доступа (только id `437954847015436288`) делайте на уровне
Discord-команд главного бота, а не полагайтесь только на права ОС.
